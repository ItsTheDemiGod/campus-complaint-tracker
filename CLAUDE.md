# Campus Complaint & Maintenance Tracker

Web portal where students report hostel/lab/Wi-Fi/electrical/plumbing issues, staff resolve assigned tickets, and admins manage staff and assignments. On assignment, an automated WhatsApp message (issue details + deadline) is sent to the assigned staff member. Software Engineering class project.

## Roles
- **Student**: submit complaints, view own ticket status, get notified on updates.
- **Staff**: has `phone_number` and `role_category` (electrician, plumber, network technician, carpenter, general maintenance). Views assigned tickets, updates status, adds resolution notes.
- **Admin**: assigns tickets to staff, sets category and deadline, manages staff accounts (incl. phone numbers and role_category), views all tickets and analytics.

## Status workflow
Open -> Assigned -> In Progress -> Resolved -> Closed
(Reopened if a student is unsatisfied after Resolved.)

## Architecture / tech stack
- **Supabase** (hosted Postgres + Auth + Row Level Security) is the data and auth layer. It owns the schema, signup/login, and role-based access (via RLS). Replaces the earlier custom-JWT/Express-CRUD plan.
- **Frontend**: React (**Vite**) + `@supabase/supabase-js`. The frontend does all CRUD directly against Supabase; permissions are enforced by RLS, not by an API layer.
- **Backend**: Node.js + Express as a lightweight **automation/notification microservice only**. It does NOT own the schema or auth and has no CRUD routes. Two jobs (later phases):
  1. Receive a Supabase Database Webhook on ticket assignment and send the Twilio WhatsApp message.
  2. Run a cron job that finds overdue tickets and sends reminder/escalation messages.
- **WhatsApp**: Twilio WhatsApp Sandbox API (Phase 6).

### Key rules
- **Never expose the Supabase `service_role` key to the frontend.** Only the anon/public key goes in frontend env vars (`VITE_*`). The service_role key is backend-only (Express automation service); it bypasses RLS.
- Any table the frontend touches must have RLS enabled with explicit policies.

## Conventions
- All secrets live in `.env` files, never hardcoded. `.env` is gitignored; keep both `.env.example` files current (names only).
- `/frontend` and `/backend` are separate top-level folders.
- Backend structure: `routes` (webhook/health endpoints), `controllers` (handlers), `middleware` (e.g. webhook secret check), `config` (env, Supabase client).
- Backend loads the root `.env` (`dotenv` with path `../.env`). Frontend uses Vite's own `frontend/.env`.
- `backend/config/supabaseClient.js` throws on require if the env vars are empty, so only require it from code that needs it.
